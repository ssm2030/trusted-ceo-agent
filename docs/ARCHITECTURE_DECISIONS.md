# Trusted CEO Agent Architecture Decisions

- 상태: Working Draft v0.1
- 기준일: 2026-07-17
- 문서 역할: 확정된 기술·운영 결정을 보존하는 정본

## AD-01. 예선 플러그인과 본선 플러그인을 분리한다

### 결정

본선용 `trusted-ceo-agent`를 별도 프로젝트로 만들고 기존 `pwc-business-issue-plugin`과 `submission.zip`은 읽기 전용 기준선으로 보존한다.

### 이유

사용자, 미션, 입력 전제, 분석 범위, 결과물이 모두 바뀌었으므로 기존 수익성 진단 흐름을 직접 개조하면 고정 가정과 회귀 위험이 남는다.

### 재사용 범위

정규화, 데이터 품질, 결정적 계산, 원본 추적, Evidence Chain, HITL, 검증 원칙만 선별 재사용한다. 수익성 플레이북 고정, 프로젝트형 B2B 전제, 내부 A/B 패키지 표현은 승계하지 않는다.

## AD-02. 네 층과 공통 Trust Kernel을 사용한다

### 결정

시스템은 `Evidence Core → Pack Stack → Bounded AI Reasoning → Human Decision` 네 층으로 나누고 Trust Kernel이 전 층을 통제한다.

### 이유

계산 가능한 사실, 도메인 지식, AI 해석, 인간 책임을 분리해야 유연성과 신뢰성을 동시에 확보할 수 있다.

## AD-03. Pack Stack은 Mission·Domain·Problem으로 분리한다

### Mission Pack

CEO 요청을 우선 검증하되 고객 가설에 끌려가지 않고 반대 관점을 확인하는 공통 정책, 결과물, 전문 경계를 저장한다. 본선 동안 거의 고정한다.

### Domain Pack

산업·사업모델 용어, KPI, 기대 관계, 가능한 원인 메커니즘, 필요 데이터, 금지 해석, 전문가 트리거를 제공한다.

### Problem Pack

발견된 문제 후보를 검증할 분석 부품, 지지·기각 조건, 필요 데이터, 중단 조건, 조건부 대응 유형을 제공한다. 문제를 미리 고정하지 않고 신호 발견 후 선택·조립한다.

### 권한 수준

- Full: 검증된 범위에서 심화 분석과 조건부 대응 허용
- Boundary: 적용 경계, 필요한 데이터, 금지 분석, 안전 중단만 제공
- Provisional: 당일 작성 가능하나 사람 승인·스키마 검증·결론 강도 제한 필수

## AD-04. 결과 등급은 공통으로 고정한다

### 결정

결과 등급 명칭과 공통 의미는 Trust Kernel/Mission Pack에 둔다. Domain Pack은 산업별 중요성·긴급성·전문가 검토 판정 기준만 제공한다. 고객별 우선순위는 Mission Contract와 HITL로 반영한다.

### 이유

산업별로 등급 체계까지 바꾸면 전사·산업 간 결과 해석이 일관되지 않는다.

## AD-05. 고객 요청은 Pack이 아니라 실행 시 Mission Contract로 입력한다

### 결정

실제 고객 질문, 증상, 고객 가설, 의사결정, 기간, 우선순위, 제약은 실행별 Mission Contract에 기록한다. 요청 처리 원칙만 Mission Pack에 둔다.

### 검증 규칙

- 고객 원인 설명은 Fact로 승격하지 않는다.
- 요청한 관점과 최소 하나의 challenge 관점을 함께 검토한다.
- 고객 질문에 직접 답하되 더 중요한 숨은 문제가 있으면 별도 제시한다.

## AD-06. AI 추론은 자유형 사고가 아니라 구조화 계약으로 제한한다

### 공통 Reasoning Contract

1. Fact Register 밖의 수치를 만들지 않는다.
2. 문제 후보는 근거 Fact와 연결한다.
3. 원인 가설마다 메커니즘, 반대 증거, 다음 관찰, 필요 데이터, 지지·기각 조건을 기록한다.
4. 관점별 AI는 전사 최종 원인·중요도·해결책을 확정하지 않는다.
5. 근거가 부족하면 추가 데이터·질문 또는 판단 불가로 종료한다.
6. 전문직 결론은 Expert Review Required로 라우팅한다.

### 출력 원칙

숨겨진 chain-of-thought를 요구하거나 저장하지 않는다. 대신 사실, 기준, 결론, 반대 증거, 불확실성, 검증 방법의 구조화된 rationale을 보존한다.

## AD-07. 병렬화는 독립 작업에만 적용한다

### 병렬 가능

- 파일별 스키마·품질 검사
- 독립된 결정적 계산
- 동일한 Fact Register·Mission Contract·Pack 버전을 사용하는 관점별 진단 카드 생성
- 관점별 추가 데이터·질문 후보 생성

### Join Barrier 이후 단일 종합

- 중복 문제 병합
- 상충하는 원인 비교
- 문제 간 인과관계 구성
- 전사 중요도·긴급성 판단
- 해결책 간 충돌·의존성 판단
- 결과 등급과 CEO 최종 서술

### 판정 원칙

다른 작업의 결과 없이 완결되는 일은 병렬 처리한다. 다른 결과와 비교해야 의미가 확정되는 일은 Join Barrier 이후 처리한다.

### 검증

코드 계산은 순차·병렬 결과가 정확히 같아야 한다. AI 결과는 핵심 신호·근거·라우팅 불변성과 반복 안정성으로 평가한다.

## AD-08. 관점별 AI는 진단 카드만 반환한다

### 카드 필드 방향

- lens/profile ID
- 사용 Fact·Signal ID
- 관찰 사실
- 경영적 의미
- 문제 후보
- 원인·반대 가설
- 필요한 확인
- 불확실성·전문가 트리거

장문 자유 보고서는 금지하고 종합 AI가 비교 가능한 제한된 형식만 허용한다. 관점이 많으면 재무·사업, 운영·인력, 리스크·통제 단위로 계층 종합한다.

## AD-09. HITL은 형식적 승인이 아니라 결과를 바꾸는 의사결정이다

### 사람의 역할

- 모호한 데이터 의미와 사업 맥락 확인
- 의도된 전략과 실제 이상 구분
- 중요도·범위·추가 분석 우선순위 결정
- AI 가설 반박·보완
- 전문가 검토, 조건부 대응, 고객 전달 승인

### 최소 게이트 방향

- 데이터 의미 확인: 모호할 때
- 문제 후보·심화 범위 승인: 필수
- 최종 대응·전문가 이관·고객 전달 승인: 필수

정확한 상태 전이와 승인 스키마는 상세 설계에서 확정한다.

## AD-10. 유연성은 변경 권한 수준으로 통제한다

### Green: 당일 안전 변경

- 입력 파일·열·단위 매핑
- 회사·산업·사업모델·기간·CEO 질문
- 검증된 Pack 선택
- 등록 분석 부품 조합
- 출력 강조점

### Yellow: 승인·테스트 후 변경

- Provisional Domain/Problem Pack
- 새 KPI·임계값
- 새 계산식·분석 부품
- 새 전문가 트리거

Yellow 변경은 승인, 입력·출력 계약, 검산, 최소 테스트, 버전 기록, 결론 강도 제한이 필요하다.

### Red: 당일 변경 금지

- 원본 보존
- Evidence Chain과 사실·해석 분리
- HITL 게이트
- 전문직 경계
- 판단 불가 정책
- 최종 Validator와 감사 로그

## AD-11. 플러그인과 웹은 하나의 분석 엔진을 공유한다

### 결정

플러그인이 표준 중간 JSON과 최종 패키지를 생성하는 정본 엔진이다. 웹은 같은 상태와 산출물을 표시·검토·질의하는 얇은 인터페이스로 시작한다.

### 이유

웹에서 분석 로직을 중복 구현하면 플러그인과 웹의 결론·근거·로그가 달라진다.

## AD-12. 검증은 자동·반복·사람 평가를 결합한다

### 자동

- 단위·계약·통합 테스트
- 순차·병렬 동등성
- 스키마·단위·무관 열 변형 테스트
- 정상·데이터 부족·충돌·미지원 도메인 안전 중단
- 동일 입력 10회 반복 안정성

### 사람

- 문제 정의 타당성
- 의사결정 유용성
- 반대 가설 품질
- CEO 가독성
- 전문가 패킷 실용성

LLM 기반 평가는 보조 수단일 수 있으나 단독 합격 판정으로 사용하지 않는다.

## AD-13. POC는 전체 수직 시나리오와 실패 사례로 증명한다

POC는 데이터 파일 선택만이 아니라 회사·CEO 요청·숨겨진 실제 문제·교란 신호·HITL 개입·전문가 트리거·기대 산출물·합격 기준을 포함하는 전체 시험이다.

구체 시나리오와 데이터 변형 방식은 미확정이다. 설계 단계에서 합격 기준을 먼저 확정하고 구현 후 기존 합성 데이터를 현재 미션에 맞게 변형한다.

## AD-14. 로그는 제출 증빙이며 설계 정본이 아니다

### 결정

- 공식 `log-hooks.zip`의 `.codex/hooks.json`, `.claude/settings.json`, `tools/save_log.py`를 프로젝트 루트에 유지한다.
- AI 대화는 편집·발췌 없이 JSONL로 보존한다.
- API 키·토큰·비밀번호를 대화에 입력하지 않는다.
- PRD와 이 결정문을 설계 정본으로 사용하고, 긴 로그를 새 대화의 기본 컨텍스트로 읽지 않는다.

### 현재 증빙

- 이전 준비 대화 스냅샷: `logs/codex/019f67d7-6313-76e3-bc61-7819feca71ee.jsonl`
- 새 대화 시작 후 별도 세션 로그 생성 여부를 확인한다.
